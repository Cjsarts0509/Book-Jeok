# 보안 설계 노트

요구사항 #2(철저한 보안)와 #3(관리자의 비밀번호 열람)은 본질적으로 충돌합니다.
비밀번호를 "열람 가능"하게 하려면 평문 또는 가역 형태로 저장해야 하는데,
이는 일반적인 보안 원칙(단방향 해시 저장)에 어긋납니다.

## 북적북적의 절충안
계정마다 비밀번호를 **두 가지 형태**로 저장합니다.

| 컬럼 | 용도 | 방식 |
|---|---|---|
| `password_hash` | 로그인 인증 | **bcrypt** (cost 12, 단방향) |
| `password_enc` | 관리자 열람 | **AES-256-GCM** (가역, 마스터 키 필요) |

- 로그인은 언제나 bcrypt 해시로만 검증합니다. 평문/복호화 값을 인증에 쓰지 않습니다.
- 관리자 "암호 열람"은 `MASTER_KEY` 로 `password_enc` 를 복호화해 보여줍니다.
- **DB만 유출되어도** `MASTER_KEY`(서버 환경변수, DB와 분리 보관)가 없으면
  비밀번호를 복원할 수 없습니다.
- 모든 열람은 `audit_log` 에 `view_password` 로 기록됩니다.

## 운영 권장
- `MASTER_KEY`, `JWT_SECRET` 는 `openssl rand -hex 32` 로 생성하고 절대 커밋 금지.
- `MASTER_KEY` 는 가능하면 OCI Vault / 환경변수 주입으로 관리하고 DB 백업과 물리적으로 분리.
- 관리자 페이지는 Cloudflare Access(OTP)로 2차 보호 권장.
- 정말로 최고 수준의 보안이 필요하다면 #3(암호 열람)을 포기하고
  "관리자는 열람 대신 재설정만 가능"으로 바꾸는 것을 권장합니다.
  그 경우 `password_enc` 컬럼과 `GET /users/:id/password` 엔드포인트를 제거하면 됩니다.

## 적용된 그 외 보안 장치
- JWT(HttpOnly 쿠키 + Bearer), 8시간 만료
- 로그인 브루트포스 레이트리밋(15분당 10회), 전역 레이트리밋
- helmet 보안 헤더, CORS 화이트리스트
- 경로 순회(path traversal) 방지: 저장 파일명은 UUID, 폴더 경로 정규화
- 계정별 저장 디렉터리 격리, 소유자/관리자 외 접근 차단
- 감사 로그(로그인/업로드/다운로드/삭제/계정변경/암호열람)
- SQL 파라미터 바인딩(인젝션 방지)
